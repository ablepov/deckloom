Deckloom развивается в инструмент создания, сохранения, просмотра и экспорта презентаций. Пользователь сможет собрать новую презентацию из готовых слайдов, изменить содержание её экземпляров, добавить собственные слайды из разрешённых блоков, поменять порядок и получить PNG, PDF и PowerPoint. Движок обеспечивает общие операции и проверки; конкретный потребитель предоставляет оформление, композиции, ресурсы и содержание.

Основания решений, ограничения текущего кода и результаты независимого ревью находятся в [архитектурном ревью](reviews/platform-review-2026-10-19.md). Этот документ — основной план развития. Изменения направления и статуса отражаются здесь; детали отдельной работы остаются в её записи.

## Результат для пользователя

1. Создать проект и новую презентацию либо открыть сохранённую.
2. Выбрать готовые слайды из подключённых библиотек, добавить их в нужном порядке, при необходимости повторить один шаблон несколько раз.
3. Изменить текст, изображения и поддерживаемую тему отдельного экземпляра без изменения библиотечного оригинала.
4. Создать собственный слайд из доступных блоков и композиций. Скрыть необязательные блоки или поменять порядок там, где композиция разрешает такую операцию.
5. Сохранить презентацию, закрыть инструмент и открыть её снова с тем же составом и содержанием.
6. Получить изображения, PDF или PowerPoint выбранной презентации с понятным результатом проверки и отчётом о неподдерживаемых возможностях.
7. Сохранить собственный слайд как новый библиотечный вариант, если он пригоден для повторного использования.
8. Организовать несколько презентаций в наборы. Подключать тематически и визуально разные проекты к одному движку.

Первая версия редактирования управляет полями и допустимыми операциями композиции. Свободное размещение любых объектов на холсте, совместная работа в реальном времени, облачный сервис и импорт изменений из PPTX обратно в исходники не входят в начальную цель.

## Состояние платформы

В 0.1.0 уже есть CommonJS API, CLI, локальный HTTP-сервер, просмотрщик, HTML/PNG-рендер и параметризованная layout QA. Есть нейтральные горизонтальная и вертикальная колоды и интеграционные тесты. Общих PDF/PPTX-экспортёров, сохраняемого документа презентации, библиотечного API и редактора ещё нет.

Контракт пока неполон: состав рендера берётся из конфигурации, состав просмотра — из папок; валидация точек входа различается; размеры отдельного слайда теряются при сканировании. Произвольный HTML не имеет гарантированного одинакового поведения в просмотрщике и Chromium-рендере. Сначала устраняются эти расхождения.

## Два способа подключения

**HTML через адаптер.** Проект предоставляет реестр колод и функцию получения документа. Он может пользоваться просмотром, диагностикой и экспортом без библиотеки шаблонов. Существующее подключение сохраняется через документированный адаптер совместимости. Произвольный HTML не становится автоматически редактируемым набором блоков.

**Управляемый документ.** Проект использует определения шаблонов, экземпляры и профили композиций. Движок может валидировать поля, менять порядок, сохранять локальные правки и предоставлять интерфейс редактирования. HTML остаётся основным представлением для просмотра и PNG/PDF. Для PPTX поддерживаемые блоки могут предоставлять отдельное структурированное представление.

Оба способа сводятся к общей подготовленной презентации: упорядоченный список слайдов с устойчивыми ID, размерами, ресурсами и известными возможностями. Это внутренний контракт рендера и экспортёров. Управляемая модель не становится обязательным входом для каждого HTML-потребителя.

## Целевая модель данных

Имена ниже описывают смысл сущностей; точный синтаксис утверждается в задачах контрактов.

| Сущность | Назначение и инвариант |
| --- | --- |
| Проект | Конфигурация, подключённые библиотеки, профили оформления и место хранения; граница разрешения ресурсов |
| Презентация, или колода | Упорядоченный список экземпляров, настройки и собственный ID; термин `deck` сохраняется для совместимости |
| Набор презентаций | Именованный список ссылок по постоянным ID презентаций в объявленной области проекта; добавление в набор не создаёт вторую копию документа |
| Определение слайда | Библиотечный шаблон с ID и ревизией, композицией, данными по умолчанию и описанием доступных полей |
| Экземпляр слайда | Собственный ID и один из вариантов содержимого: ссылка на шаблон с локальными изменениями, локальная композиция или данные HTML-адаптера; номер показа вычисляется из порядка |
| Композиция | Версионируемая раскладка, слоты, правила вместимости, разрешённые темы и операции |
| Определение блока | Тип и ревизия, схема данных, renderer и возможности экспорта; вложенность и перестановки разрешены явно |
| Экземпляр блока | Собственный ID, ссылка на тип/ревизию и значения полей; принадлежит контейнеру, который хранит порядок его дочерних ID |
| Ресурс | ID, ревизия или хеш, тип, источник и способ доставки; размещение и crop принадлежат использующему блоку |
| Профиль оформления | Версионируемые роли и ресурсы проекта; перечень поддерживаемых вариантов |
| Снимок сборки | Разрешённые данные, версии реализаций, HTML, ресурсы и сведения о среде; материал для повторного просмотра и экспорта |

ID, порядок и имя файла — разные свойства. Повторное добавление одного шаблона создаёт новый экземпляр. Переупорядочивание не меняет его идентичность. Локальная правка не обновляет библиотечный оригинал. Публикация новой ревизии или сохранение нового варианта — отдельная явная операция.

Локальная композиция хранится в самой презентации и не требует предварительного библиотечного определения. Её явное сохранение в библиотеку создаёт такое определение и ревизию. Данные HTML-адаптера содержат версионируемую ссылку на адаптер и сериализуемую полезную нагрузку или ссылку на исходник; исполняемый callback не становится частью документа.

Переименование документа сохраняет его ID, дублирование создаёт новый. Перемещение проверяется относительно области проекта и реестра ресурсов. Удаление связанной презентации оставляет явное состояние отсутствующей ссылки; другой файл с тем же именем не подменяет документ.

Сохранение редактируемого документа и сохранение результата сборки решают разные задачи. Для повторного редактирования нужны совместимые версии композиций и renderer. Если они недоступны, сохранённый HTML-снимок может оставаться пригодным для просмотра, но не объявляется полностью редактируемым.

Снимок объявляет восстанавливаемые форматы отдельно. HTML и включённые ресурсы достаточны для поддерживаемого просмотра и PNG/PDF в совместимой среде. Автономный редактируемый PPTX дополнительно требует сохранённого подготовленного экспортного представления или доступных закреплённых реализаций блоков/экспортёра. Один список версий этого не обеспечивает.

## Принципы экспорта

PNG и PDF используют одно подготовленное содержание, размеры и ресурсы. Поддерживаются вся презентация и выборка с сохранением порядка Deck; перестановка задаётся самим документом, а не параметром формата. Изменение формата не меняет исходные данные.

Для PowerPoint различаются три результата: слайды как изображения; редактируемые текст и простые фигуры с отдельными графическими ресурсами; поддерживаемые структурированные блоки с собственным PPTX-представлением. Векторный SVG сам по себе ещё не означает редактирование отдельных объектов в PowerPoint.

Цель — надёжный экспорт с редактируемыми текстом и поддерживаемыми блоками. Растровые фотографии и сложная графика могут оставаться изображениями. Подмена целого слайда картинкой допускается только в явно выбранном режиме. По умолчанию такая потеря редактируемости должна быть видна в отчёте или останавливать строгий экспорт.

Структурированный экспорт не получает отдельную несвязанную копию текста и порядка. Он использует разрешённые данные и стили той же подготовленной презентации; измеренная геометрия или поддерживаемое export-представление передаются через общий контракт. Различия в переносах и геометрии PowerPoint проверяются на заявленном подмножестве.

Проба PPTX выполняется рано, до закрепления окончательного контракта блоков. Если DOM-конвертация не проходит критерии, результатом пробы становится структурированный backend или ограниченный гибрид, а не обещание универсального HTML → редактируемый PPTX.

Базовый профиль ориентирован на статическое содержимое. В C1 сравниваются изолированный document preview и текущая вставка HTML с переписыванием CSS: выделение текста, поддержка head/resources, шрифты, масштаб и отсутствие влияния стилей проверяются на одинаковых примерах. Способ preview выбирается по этому результату. HTML, зависящий от выполнения JavaScript, требует отдельного способа подготовки в статический результат или явно поддержанного расширения. Изоляция CSS не объявляется изоляцией недоверенного кода.

Произвольная диаграмма, таблица и фирменная сцена могут предоставляться отдельным блоком с ограниченными полями. Поддержка обычной перестановки карточек не обещает автоматический пересчёт связей любой схемы.

### Этап J Несколько проектов и стабилизация

| Шаг | Ограниченный результат | Критерий завершения |
| --- | --- | --- |
| J1 | Наборы презентаций и выбор проекта | Несколько документов объединяются без копирования; ресурсы и локальное состояние разных проектов не смешиваются |
| J2 | Второй независимый профиль потребителя | Визуально другой нейтральный проект и затем отдельный реальный адаптер используют тот же публичный API; фирменные исключения остаются в профиле |
| J3 | Стабилизация публичного API и измерение практических ограничений | Есть migration guide, документация, проверенный диапазон среды, производительность на малой и большой колоде; границы поддержки заявлены |

Нейтральный второй профиль используется уже на B–F для проверки архитектуры. Миграция отдельного реального потребителя не блокирует развитие ядра и выполняется самостоятельной задачей, когда это полезно. Стабильность ядра и готовность всех будущих функций не обязаны наступить одним релизом.

## Зависимости и приоритет

Общая основа: A → B → минимальный C. Затем экспортная ветка D и документная ветка F1–F2/G1 могут развиваться независимо; редактор не ждёт завершения переносимого экспорта всех форматов. E1–E2 проверяют PowerPoint рано, до закрепления export-capabilities F3. Если PowerPoint недоступен, базовый документ и неэкспортные операции продолжаются, а неподтверждённые возможности остаются явно обозначенными.

После минимального F3 доступны F4, G2–G4 и приложение H; надёжный save/reopen H требует G1. Custom-слайды I опираются на F3/F4 и хранение. E3 требует D1/E2 и ресурсов; для структурированного backend — также минимального F3 или согласованного export-представления. I и E4 добавляют проверку новых блоков. J1 требует сохранения документов, J2 проверяется постепенно, J3 завершается по выбранной стабильной области API. Схема задаёт технические зависимости, а не разрешение нескольким авторам одновременно менять один checkout.

Первые три результата, полезные отдельно:

1. **Согласованное ядро:** одинаковые состав, порядок, размеры, HTML и диагностика в просмотре и рендере.
2. **Экспортный инструмент:** PNG/PDF и проверенная стратегия PowerPoint с точными границами поддержки.
3. **Сохраняемая презентация:** шаблоны и независимые экземпляры, операции и reopen через API. На этой основе появляется интерфейс.

Архитектура планируется целиком, но каждый результат выпускается небольшими изменениями. Блоковый редактор не нужен для начала PDF и испытания PPTX.

## Проверка каждого изменения

| Что меняется | Обязательное доказательство |
| --- | --- |
| Контракт/валидация | Положительный сценарий и существенные отрицательные случаи; одинаковые ошибки точек входа; тест миграции при изменении схемы |
| Состав/порядок/ID | Перестановка, удалённые артефакты, повтор шаблона, уникальность экземпляров и round trip |
| HTML/viewer/resources | Браузер: focus/overview, узкое окно, выделяемый текст, отсутствие утечки стилей, ресурсы и ошибка загрузки |
| Геометрия/темы | Светлый/тёмный и портретный примеры, длинная кириллица, ошибка вместимости; отсутствие скрытого autofit |
| PNG | Размеры, содержимое и визуальное сравнение в закреплённой среде |
| PDF | Число/размер страниц, извлечённый текст и шрифты, ссылки в заявленном объёме, визуальное сравнение страниц |
| PPTX | Структура, открытие без восстановления в PowerPoint, редактирование заявленных объектов, рендер в PowerPoint и отчёт о fallback |
| Хранение/версии | Reopen, изоляция правок, повреждение, прерывание записи, конфликт внешнего изменения, старая ревизия и миграция |
| Пакет/релиз | Установка архива вне репозитория, публичные imports/CLI, отсутствие частных/генерируемых материалов, подходящий consumer regression |

Общий smoke-набор охватывает нейтральные презентации с разным оформлением. Полная регрессия конкретного потребителя нужна при затронутом поведении или переходе на новую версию. Сравнение исходного и нового результата отделяет ожидаемое изменение от дефекта; намеренно исправленная ошибка не обязана сохраняться ради совпадения.

Для каждого шага в его записи сохраняются: результат, изменённый контракт, выполненные проверки, допустимые отличия, ограничения и следующая задача. Название команды не заменяет результат её выполнения. Доказательства PPTX без PowerPoint и неподтверждённая переносимость ресурсов отмечаются как частичные.

## Совместимость и развитие

Работающий потребитель не замораживает архитектуру. Breaking change допустим, если понятны его польза, затронутые интерфейсы и переход. До обновления потребитель продолжает использовать закреплённую опубликованную версию.

Для несовместимого изменения требуются:

1. Пример старого поведения, новая модель и перечень затронутых полей/команд/результатов.
2. Решение: короткий адаптер совместимости или явная миграция. Постоянная поддержка всех старых моделей не предполагается.
3. Migration guide с примером до/после и тестом. Автоматическая миграция документа сохраняет исходник.
4. Проверка пакета и нейтральных сценариев; отдельная проверка адаптера существующего потребителя в согласованной области.
5. Новый опубликованный пакет, подтверждение доступности, затем явное обновление точной зависимости потребителя и его проверки.
6. Возможность вернуть прежнюю зависимость; откат пакета не заменяет восстановление документа, уже преобразованного новой схемой.

Для 0.x предлагается локальная политика: совместимые исправления — patch, несовместимые изменения публичного контракта — следующий minor с migration guide. Это договорённость проекта: SemVer не обещает стабильный API до 1.0. После 1.0 применяется обычное разделение major/minor/patch. Версия схемы документа, ревизия шаблона и версия npm-пакета ведутся отдельно. Источник: [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
