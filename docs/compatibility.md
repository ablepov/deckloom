# Совместимость и миграции Deckloom

Политика этапа A, 20 октября 2026 года. [Roadmap](roadmap.md) задаёт направление, [исходная точка](baseline-0.1.md) — поддерживаемые сценарии и известные дефекты 0.1.0. Версии npm-пакета, схемы документа и ревизии шаблона/композиции — разные шкалы.

## Что считается публичным контрактом

Публичные package exports, документированные методы/параметры и результаты, CLI/exit codes, поддерживаемая конфигурация, HTTP API просмотрщика и заявленные пути/форматы артефактов. Имена внутренних модулей и DOM-классов viewer сами по себе не являются API, но их изменение проверяется на поведении viewer. Известный дефект не становится гарантией только потому, что он наблюдался в 0.1.0.

Расширения и исправления сохраняют подтверждённые сценарии или явно описывают переход. Требование совместимости не запрещает исправлять архитектуру, менять файловую организацию или удалять устаревшие интерфейсы.

## Версии и типы изменений

| Изменение | Версия/переход | Что проверить |
| --- | --- | --- |
| Совместимое исправление | Patch; примечание в release notes | Основной сценарий и существенный соседний случай, существующий smoke-набор |
| Совместимая новая возможность | Minor; описание нового API | Новый сценарий, старые значения по умолчанию, отсутствие обязательной миграции |
| Исправление известного дефекта | Patch, если не меняет заявленный контракт; иначе несовместимое изменение | Доказательство исправления, перечень отличий артефактов/ошибок; не сохранять дефект ради старого screenshot |
| Несовместимый публичный контракт в 0.x | Следующий minor с migration guide | Старый/новый адаптер, переход, проверка потребителя, откат |
| Несовместимый публичный контракт после 1.0 | Следующий major | То же, включая оговорённый срок удаления deprecated API |
| Изменение сохраняемой схемы | Явная schemaVersion и миграция независимо от npm-версии | Round trip, старые данные, отсутствие потери, сохранение исходника |
| Изменение шаблона/композиции/ресурса | Новая ревизия по контракту соответствующего слоя | Изоляция уже сохранённых экземпляров, точная ссылка и воспроизводимость |

Политика minor для breaking changes в 0.x — договорённость проекта, более строгая, чем базовая спецификация [SemVer](https://semver.org/spec/v2.0.0.html). Исправление может стать breaking change, если потребитель должен поменять конфигурацию, команды, интерпретацию результата или пути.

## Процедура изменения контракта

1. Сформулировать пользу изменения, действующий и новый контракт, затронутые методы/конфигурацию/файлы. Отметить, исправляется ли известный дефект.
2. Выбрать явную миграцию или небольшой временный адаптер. Для адаптера задать область и условие удаления; поддержка всех исторических моделей не предполагается.
3. Подготовить migration guide по [шаблону](migrations/template.md), реальный пример до/после и проверку перехода. Для файловых миграций сохранять исходник.
4. Проверить текущий репозиторий и установленный npm-архив. Сопоставить новый результат с исходной точкой; отдельно описать ожидаемые различия.
5. Если изменение затрагивает существующего потребителя, проверить его адаптер в отдельно согласованной области. При отсутствии этой проверки статус — «проверено ядро; готовность обновления потребителя не подтверждена».
6. Выпустить новую версию и убедиться в фактической доступности registry и tarball. Публикация — отдельное действие, не побочный эффект проверки.
7. Явно обновить точную зависимость потребителя и его lockfile, выполнить применимые проверки и сохранить результат перехода.

Нет требования сначала довести визуальную базу потребителя. Достаточно проверить то поведение, которое меняет обновление движка. Частные ресурсы и зависимости остаются у потребителя; нейтральный воспроизводимый пример общего дефекта принадлежит Deckloom.

## Регрессионная матрица

E3 аддитивно вводит `formats:['pptx']` и явные `pptx` options; существующие defaults и D strict font policy не меняются. [Переход](migrations/pptx-e3.md), [ограниченный профиль и незакрытый UI checkpoint](contracts/pptx-e3.md). Backend bundle имеет отдельные lock/inventory/notices и воспроизводимую сборку; archive consumer проверяется без overrides. Обновление потребителей и выпуск пакета не выполнены.

| Область изменения | Проверка |
| --- | --- |
| src/публичное API/CLI | `npm run check`, `npm test`, `npm run check:package`; применимые положительные и отрицательные случаи |
| viewer/server/scanner | HTTP-границы, навигация, состав и размеры, focus/overview, узкое окно и HTML/asset loading в браузере |
| renderer/QA/resources | Нейтральный пример, ошибки layout/assets/page, `npm run check:baseline`; при изменении геометрии — визуальная сверка |
| упаковка/exports/dependencies | Реальный `npm pack` и внешний потребитель; проверка manifest архива, imports и CLI; отсутствие частных/file-зависимостей |
| версии/сохранение | Проверка миграции и возврата к исходному документу; сохранение прежней зависимости не откатывает данные автоматически |

Неизменённый runtime не требует повторять полную приёмку всех материалов потребителя. Полный рендер потребителя нужен при затронутом поведении и перед заявлением готовности его обновления. Нейтральные примеры проверяют ядро, но не доказывают готовность всех частных адаптеров.

## Откат

До обновления сохраняются прежние точная зависимость и lockfile, конфигурация/адаптер и исходные данные. Откат выполняется к этим зафиксированным версиям, затем повторяется основной сценарий. Используются сохранённые артефакты и подтверждённая доступность прежнего пакета.

Если новая версия изменила формат документа, требуется прежняя копия или проверенная обратная миграция. Старый npm-пакет не должен получать уже необратимо преобразованный документ. Прежняя опубликованная версия не переписывается и не заменяется локальным архивом под тем же номером.

## Запись результата

Задача изменения хранит: старую/новую версию, затронутый контракт, выполненные команды и их результаты, ожидаемые отличия, ограничения, ссылку на migration guide и следующий шаг. Изменение кода, прохождение core-тестов, установка архива, публикация и готовность обновления потребителя — отдельные статусы.
