# Переход от API 0.1 к контракту Project Deck Slide

Этап B1, переход от 20 октября 2026 года. Целевая версия npm пока не назначена; v1 обозначает [контракт конфигурации](../contracts/project-deck-slide-v1.md). Примеры после перехода не поддерживаются опубликованным 0.1.0. B2 реализует внутренний legacy bridge без перезаписи конфигов и файлов; миграция потребителей и автоматический файловый преобразователь не выполнялись.

## Граница изменения

Меняются описание идентичности, источника состава, размеров и размещения артефактов. Функция получения HTML и брендовые данные остаются у адаптера. Существующий потребитель продолжает использовать точную опубликованную версию до отдельного обновления; переход не требует менять содержание или дизайн его слайдов.

Текущие imports и CLI dev/render остаются оболочками. Новый публичный контракт активируется явно через contractVersion, а не переосмыслением любого старого объекта. Внутренние normalize/validate функции и проекция чтения описаны для последующей реализации; в B1 они не добавляются в runtime.

## Карта полей

| 0.1 | V1/переход | Особенность |
| --- | --- | --- |
| Нет версии конфигурации | `contractVersion: 1` | Отдельно от npm и schemaVersion будущего сохраняемого документа |
| Нет Project.id | Явный постоянный project.id | Не вычислять из cwd или имени папки |
| Состав обнаруживается viewer по папкам | `mode: registered`, decks[].slides | Реестр задаёт состав и порядок |
| Только чтение существующих папок | `mode: discovery`, deck.artifactPrefix | Отдельный read-only профиль без slides |
| `root` | Абсолютный root с тем же исходным смыслом | Относительный legacy root сохраняет разрешение от cwd в bridge; при явном переходе фиксируется абсолютный путь |
| `deck.id`, `label`, `width/height` | Те же поля | Уникальность и размеры валидируются единообразно |
| `deck.artifactPrefix` | Только legacy layout | Stable layout строится по ID |
| `slide.no` | Постоянный slide.id + отдельный artifactNo для legacy | ID нельзя пересчитывать при reorder; no в данных renderer можно сохранить через wrapper |
| `slide.name` | То же | Переименование не меняет ID |
| `slide.width/height` | Те же overrides с единым наследованием | После B4 совпадают в viewer/render |
| Произвольные top-level поля deck/slide | `data` адаптера | Нельзя механически перенести функции и изменить способ их вызова; wrapper сохраняет прежний renderDocument |
| Хуки, viewer, staticMounts | Сохраняемые роли | Async renderQa уже поддерживается в 0.1 через await; дальнейшее уточнение — C3 |
| id/no/file/htmlUrl HTTP/scan | Bridge сохраняет проекцию 0.1; явный v1 отдаёт contractVersion и новую проекцию чтения | Нет no=number; viewer поддерживает обе; реализация — B3 |
| reportName после рендера | Чистое вычисление имени для preflight | Один basename, уникальный в Project без учёта регистра; hook не должен ожидать уже созданный PNG |

## Unversioned bridge

Предлагаемая переходная оболочка распознаёт конфиг без contractVersion как legacy 0.1. Неизвестная явная версия не считается legacy. Конфиг не переписывается на диске.

- Если все колоды имеют массив slides, он переводится в registered-описание. Если у всех slides отсутствует, выбирается discovery. Смешанный случай неоднозначен и требует явной миграции, а не скрытого merge.
- Unversioned-конфиг с пустым decks не классифицируется через два пустых every: viewer 0.1 его не поддерживал. Для такого черновика нужен явный v1 с выбранным mode.
- Для legacy registered конфигурации постоянный локальный ID первоначально берётся из строки no. Это допустимо только как одноразовый перенос: после него ID не перенумеровывается. Повторяющиеся no требуют явного назначения ID и различных путей.
- Исходные artifactPrefix/no и reportName сохраняют файловую организацию. Hooks и renderDocument вызываются через wrapper с прежними Deck/Slide и контекстом, а не с внезапно перенесёнными полями data.
- До явного project.id используется внутренний namespace legacy-сессии, не пригодный для сохранения и подключения нескольких проектов. Старый явный viewer.storagePrefix сохраняется. Переход к устойчивым внешним ссылкам требует назначения project.id.
- Legacy-относительные пути разрешаются от cwd в одном месте с диагностикой. Для versioned v1 они приводятся к абсолютным в конфиге; перенос в другой cwd не должен менять смысл.
- Исправление известной ошибки состава и порядка не маскируется совместимостью: registered перестаёт показывать оставшиеся папки. Для прежнего просмотра всех папок есть явный discovery.

Bridge ограничен переходом от опубликованного 0.1, а не поддержкой всех исторических форматов. Его окончательный срок удаления определяется при выпуске нового API; до этого нужна как минимум проверенная явная миграция и отдельное объявление удаления. В B2 ветви внутренней нормализации проверяются нейтральными fixtures; публичной функции `fromLegacy` нет. Изменение состава/порядка scanner и viewer остаётся B3.

### Что уже меняется в рабочей копии B2

Существующие createRenderer/createReviewServer/scanDecks/scanSlides используют общую проверку. Они раньше отвергают неверные типы и размеры, duplicate/case-only ID и prefix, несовпадение expectedSlides, недопустимые цифровые no и конфликтующие пути. Отсутствующий slides не заменяется пустым массивом, null не становится отсутствующим значением. Это ожидаемое ужесточение входа для будущего minor-релиза, а не изменение опубликованного 0.1.0.

reportName вычисляется синхронно при preflight, в том числе проверке входа для чтения; вызывается для всех колод Project, а не только отрендеренных. Пустая строка/Promise/небезопасное имя — ошибка вместо прежнего fallback. Hook должен быть чистым и не зависеть от существования результата рендера. Raw callbacks по-прежнему получают исходные Deck/Slide; состав, файловые ключи, размеры и пути движка фиксируются до первого await операции. Данные адаптера при этом не копируются и могут оставаться изменяемыми.

Полный --deck=all проходит preflight до запуска Chromium/первой записи, а затем выполняет один подготовленный план. Изменение массива колод/слайдов callback-ом не расширяет текущую операцию. Неудачная валидация не создаёт outputRoot; она не является транзакцией для последующей ошибки HTML, Chromium, callback или изменения файловой системы внешним процессом.

B2 не переключал старый HTTP payload и не исправлял состав scanner за счёт новой модели. Внутренний модуль src/project.cjs не добавлен в package exports. Следующий B3 подключает [чтение](../contracts/read-api-v1.md); полная поддержка нового конфига, включая renderer, объявляется после B4.

### Что уже меняется в рабочей копии B3

Registered scanner/server/viewer используют реестр: исключённые слайды не возвращаются по оставшимся папкам, порядок берётся из slides, отсутствующие артефакты не исключают зарегистрированный экземпляр. HTTP-форма старого входа сохраняется, но появляются null URL/file у placeholders; no остаётся файловым ключом. Старое ранжирование preview сохранено для unversioned registered и discovery. V1 registered читает стандартный generated-html.png по B1.

Если нужен прежний поиск всех папок, следует явно выбрать discovery, убрав slides у всех колод (в v1 также задать mode и legacy layout). Discovery доступен только для чтения. scanSlides теперь выбирает каноническую колоду по ID; переданные в selection slides/другие поля не подменяют реестр. Server snapshot фиксируется при создании; обновить конфиг можно перезапуском, изменение файлов видно через polling.

На этапе B3 versioned чтение стало доступно, а renderer ещё оставался закрыт. Проекция одного v1 Deck вложена в deck, поля artifacts заменяют legacy file/htmlUrl. В v1 нет no. URL выдаётся сервером под /artifacts/<relative-path>, а hash viewer включает project/deck/slide; старый hash не является автоматически новым ID. Legacy layout сохраняет unprefixed file aliases. Явные staticMounts зеркалируются под /artifacts/ для относительных ресурсов legacy HTML; незаявленные папки не публикуются. Точные поля и aliases описаны в [проекциях B3](../contracts/read-api-v1.md).

### Что уже меняется в рабочей копии B4

V1 renderer открыт. renderDeck выбирает колоду по строке ID либо object.id из канонического реестра; дополнительные поля selection не подменяют v1 slides/размеры. Unversioned raw-deck override сохранён. V1 callbacks получают нормализованные метаданные с data и эффективными размерами; старые callbacks по-прежнему получают исходные объекты через bridge. Default v1 QA не сериализует произвольный data; report.slide — постоянный ID, index/number/width/height задаются отдельно. Старый report.slide остаётся no.

Перенос адаптера на v1 требует использовать slide.width/height в HTML: renderer/API/viewer применяют вычисленные размеры, но не исправляют авторский CSS молча. Текущий PNG budget — сторона до 16384 px и площадь до 64 × 1024 × 1024 пикселей, ошибка UNSUPPORTED_CANVAS до записи. Это ограничение backend-профиля, а не логической схемы B1.

Read preflight больше не отвергает весь Project из-за одного повреждённого leaf. У HTML и PNG независимые состояния missing/available/unreadable. Unversioned DTO дополнен необязательными htmlError/imageError только при unreadable; прежние положительные поля и URL сохраняются. Viewer не маскирует unreadable/failed HTML PNG-картинкой и повторяет временные ошибки при healthy polling. Строгие physical проверки перед записью сохранены. Дальнейшие изменения HTML/resource profile, hooks/results и freshness остаются C1–C4; детали — в [контракте B4](../contracts/render-v1.md).

Сохранение путей через artifactNo покрывает цифровые no. Текущий renderer может создавать `prefix-intro` для буквенного no, но scanner 0.1 уже не умеет его обнаруживать. Такой вход не переносится автоматически в цифровой legacy layout: нужны явная таблица новых путей и адаптация ссылок/ресурсов либо отдельный согласованный compatibility-профиль. Bridge выдаёт диагностируемую несовместимость, а не переименовывает файл молча. Дубликаты prefix, case-only ID и конфликтующие reportName также требуют явного разрешения.

## До перехода

Минимальный исполняемый конфиг 0.1:

```js
const path = require('node:path');
module.exports = {
  root: path.join(__dirname, 'output'),
  decks: [{
    id: 'intro', label: 'Введение', artifactPrefix: 'demo-slide', width: 1280, height: 720,
    slides: [{ no: '01', name: 'Обложка', text: 'Пример' }],
  }],
  renderDocument(deck, slide) {
    return `<!doctype html><html><head><meta charset="utf-8"></head><body><main class="slide">${slide.text}</main></body></html>`;
  },
};
```

## После перехода с сохранением путей

Этот пример сохраняет старый HTML-адаптер через явные обёртки. Файл `legacy.config.cjs` означает сохранённую конфигурацию из предыдущего примера в том же каталоге; код v1 не исполняется текущим движком.

```js
const legacy = require('./legacy.config.cjs');
// Materialized once during migration; do not derive IDs from array positions.
const bindings = { intro: { '01': { id: 'intro-cover', artifactNo: '01' } } };
const decks = legacy.decks.map(deck => {
  const slides = deck.slides.map(slide => {
    const binding = bindings[deck.id]?.[slide.no];
    if (!binding) throw new Error(`Missing migration binding for ${deck.id}/${slide.no}`);
    return { ...binding, name: slide.name, width: slide.width, height: slide.height, data: { source: slide } };
  });
  return { id: deck.id, label: deck.label, artifactPrefix: deck.artifactPrefix, width: deck.width, height: deck.height, slides, data: { source: deck } };
});
module.exports = {
  contractVersion: 1, id: 'neutral-project', mode: 'registered',
  root: legacy.root, artifacts: { layout: 'legacy' }, decks,
  renderDocument(deck, slide, context) {
    return legacy.renderDocument(deck.data.source, slide.data.source, context);
  },
};
```

Обёртка использует data.source, а не идентичность JavaScript-объекта, поэтому нормализация с копированием метаданных не должна ломать её. Если исходный конфиг содержит hooks или viewer/staticMounts, они переносятся отдельно с сохранением прежних аргументов. Ни один такой hook не заменяется предположением о форме нового объекта.

Для реальной миграции таблица привязок `(deck.id, старый no) → новый slide.id/artifactNo` сохраняется явно. Исходный no используется только как ключ старого источника, а не как новый номер показа. Последующее изменение порядка не запускает генерацию ID заново. Для примера после перестановки по-прежнему используется id intro-cover.

## Сохранение и изменение путей

Legacy layout сохраняет `demo-slide-01/demo-slide-01-render.html` и `generated-html.png`. Stable layout переносит результат в `deck-intro/slide-<id>/render.html`. При выборе stable нужно отдельно адаптировать относительные assets, статические mounts и внешние ссылки. Нельзя одновременно обещать сохранение старого имени файла и его автоматическое вычисление из новой позиции.

Старые bookmarks, сохранённый viewer state и интеграции с HTTP/report полями проверяются отдельно. Unversioned input остаётся на проекции чтения 0.1; переход конфигурации на contractVersion1 требует перевести прямых HTTP/scan-клиентов на v1-поля и проверку версии. Вложенные artifacts заменяют file/htmlUrl; id — ID экземпляра, number — позиция. Legacy route/ID aliases могут предоставляться временно; точные aliases и их проверка относятся к B3. B1 не заявляет, что произвольный старый hash автоматически работает при новом layout.

## Порядок будущего перехода

1. Зафиксировать старый npm/lockfile, конфиг, данные, пути и значимые результаты.
2. Выбрать registered либо discovery; назначить project.id и устойчивые ID; разрешить дубликаты без автоматической потери слайдов.
3. Сначала оставить legacy layout и прежний HTML через wrapper. Перенос на stable layout выполнить отдельно, если он нужен.
4. После реализации B2–B4 проверить packed candidate: старый путь через bridge и явный v1-конфиг, положительные и отрицательные случаи контракта.
5. Проверить ID/order/delete/missing-artifacts/dimensions и важные aliases; сравнить HTML/PNG. Изменение порядка и исключение старых папок описать как ожидаемый результат.
6. Отдельной задачей проверить адаптер конкретного потребителя и только затем явно обновлять его точную зависимость после публикации доступной версии.

Пока эта последовательность не выполнена, статус — «проект перехода», а не «потребитель мигрирован». Необходимый minor-релиз 0.x и release notes назначаются по реально реализованному объёму, а не в B1.

## Откат

Вернуть прежние dependency/lockfile и конфиг, использовать сохранённые исходные данные и артефакты. Новая runtime-конфигурация пока не записывает документы F, поэтому миграция схемы сохранённых презентаций здесь не выдумывается. Если при переходе менялись сами пути или ресурсы, вернуть их исходную копию; откат npm-версии один не восстанавливает перемещённые файлы.
