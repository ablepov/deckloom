# Архитектурное ревью Deckloom

Дата: 19 октября 2026 года. Исходная точка: версия 0.1.0, коммит `10bc6339a8dbb688b083855b9fade2a0f44438ea`. Область: публичный движок, API, расширение до сохраняемых презентаций и экспорта. Доработки содержания и оформления потребителей сюда не входят.

Результирующий план находится в [roadmap](../roadmap.md). Требования к конечному инструменту: создание и сохранение презентаций и их наборов, порядок слайдов, независимые экземпляры шаблонов, локальные правки, custom-слайды из готовых блоков, PNG/PDF/PowerPoint. Совместимость существующего потребителя важна, но осознанная миграция допустима.

## Текущее ядро

Публичные entry points: `deckloom`, `deckloom/node`, `deckloom/qa`. Реализованы `createReviewServer`, `startReviewServer`, `createRenderer`, `scanSlides`, `scanDecks`, layout measure и счётчик ошибок. CLI поддерживает dev/render. Есть viewer, PNG, HTML, опциональные spec и QA, настраиваемые хуки.

Пакет использует Node.js >=22, Playwright peer >=1.57 <2; dev-зависимость 1.59.1. CI выполняет проверки на Ubuntu/Node 22. Матрица всего заявленного диапазона среды пока не проверяется. OIDC publish workflow присутствует; его наличие само по себе не подтверждает настройку npm Trusted Publisher.

## Наблюдения по контракту

| Наблюдение | Доказательство | Значение для развития |
| --- | --- | --- |
| Два источника состава | [renderer](../../src/renderer.cjs) проходит `deck.slides`; [scanner](../../src/artifacts.cjs) ищет цифровые папки и сортирует их | Один источник состава должен предшествовать сборке, сохранению и экспорту |
| Scanner включает старые артефакты | В нейтральном примере конфигурация только с `02` возвращает `01`, `02` | Удаление/выборка не имеют общей семантики |
| Порядок теряется | Заданные `02`, `01` возвращаются как `01`, `02` | Сохранённая презентация не может полагаться на текущее сканирование |
| Идентификаторы неоднородны | Renderer допускает безопасную строку `intro`, scanner/server artifact route распознают цифровое окончание; дубликаты slide.no принимаются | Нужны валидируемая идентичность и отдельный порядок |
| Размер слайда теряется | Renderer читает slide.width/height, scanner возвращает deck.width/height | Подготовленный дескриптор должен использоваться всеми форматами |
| Валидация различается | [server](../../src/server.cjs) отвергает повтор deck.id и width=0; конструктор renderer принимает | Проверка входа должна быть общей и происходить до записи |
| HTML зависит от PNG при обнаружении | Scanner пропускает папку без подходящей картинки, даже если HTML есть | Нужны явные состояния доступных артефактов |
| HTML-профиль не определён полностью | [viewer](../../viewer/index.html) удаляет scripts, берёт style и body; link stylesheet из head теряется | Нельзя обещать одинаковый произвольный HTML в viewer и renderer |
| API рендера связан с CLI | `run()` принимает argv, печатает и меняет process.exitCode; renderDeck возвращает report с QA-сбоями | Нужны чистый программный результат и CLI-адаптер |
| Асинхронность хуков неодинакова | renderDocument/renderSpec/validateDocument/renderQa await; reportName и issueCount синхронные | Типы/async/среда каждого хука должны стать контрактом |
| Ресурсы и готовность частичны | Ожидание fonts.ready и img; отдельного полного отчёта по CSS/fonts/background/SVG нет | Нужна проверяемая readiness-политика и переносимая подготовка |
| Публикация артефактов пофайловая | writeArtifact атомарен для файла, сборка пишет HTML раньше PNG и report | Нужен способ связать результаты одной успешной/неуспешной сборки |
| Модель редактирования отсутствует | Публичное API работает с конфигурацией/HTML/артефактами | Сохранение и blocks API — новые слои с миграцией, а не расширение сканера папок |

Это ревью различает наблюдаемый дефект, неполный контракт и будущую возможность. Отсутствие редактора или PDF соответствует заявленной области 0.1.0 и само по себе не является ошибкой текущей версии.

## Рассмотренные направления

| Решение | Польза | Издержки | Вывод |
| --- | --- | --- | --- |
| Обязать все проекты сразу перейти на общую модель blocks | Единый редактор и экспорты | Дорогая миграция, потеря произвольных фирменных композиций, преждевременная схема | Сохранить HTML-адаптер и добавить управляемый слой отдельно |
| Оставить только HTML и менять DOM редактором | Быстрый старт на текущем формате | Неявные поля/операции, хрупкие CSS-правки, слабое сохранение идентичности | HTML использовать как представление; редактирование — через валидируемые данные |
| Продолжать переписывание CSS либо изолировать документ preview | Inline упрощает интеграцию; отдельный документ лучше сохраняет семантику HTML/CSS | Inline расширяет поверхность несовместимости; отдельный документ требует проверить масштаб, загрузку и взаимодействие | Выбрать по нейтральной матрице C1; PNG fallback не заменяет заявленный selectable HTML |
| Сначала редактор, потом документ и экспорт | Рано появляется видимый интерфейс | UI закрепляет случайные ограничения хранения и export | Сначала документ/команды и ранняя проверка PPTX, затем UI |
| Сначала полностью универсальный PPTX | Один обещанный результат для любого HTML | Неподтверждённая полнота CSS/шрифтов и редактируемости | Ранняя ограниченная проба, затем поддерживаемый контракт и отчёт о потерях |
| Сохранить все детали 0.1.0 навсегда | Минимальная работа потребителя сейчас | Устройство папок и ошибки становятся архитектурными ограничениями | Пин версии, ограниченный compatibility adapter или явная миграция |
| Переписать ядро целиком перед полезными результатами | Возможность заново организовать код | Большой риск и долгое отсутствие проверяемого результата | Изменять контракт небольшими вертикальными шагами |
| Немедленно разделить платформу на множество npm-пакетов | Явные границы зависимостей | Дополнительные релизы и совместимость до стабилизации API | Сначала модули и интерфейсы; выделять пакеты по реальной потребности |

## Проверки исходной точки

19 октября выполнены `npm run check` — 9 модулей и viewer script; `npm test` — 5 тестов, все прошли. Тесты покрывают основные HTTP-границы, viewer, две геометрии колод, настраиваемую QA, отсутствующие изображения и page errors. Это не проверка PDF, PPTX, сохранения или редактирования.

Дополнительные узкие проверки через публичные API подтвердили различие валидации, порядка, состава и размеров. На существующих нейтральных артефактах результат scanner проверялся без записи файлов; отсутствие PNG моделировалось только в памяти. В Chromium проверено, что normalization сохраняет встроенные стили и удаляет scripts, но теряет stylesheet link из head. Эти наблюдения воспроизводят ограничения; новые постоянные тесты ещё не добавлены.

## Независимая проверка решений

Выполнены два независимых разбора: архитектура/границы слоёв и экспортные стратегии/проверки по первичным источникам. После подготовки roadmap каждый разбор получил второй критический проход по своему предмету. Основной автор сопоставил замечания с кодом и зависимостями этапов.

Архитектурный разбор подтвердил две формы авторства, отдельный документ до UI и миграцию вместо постоянной заморозки API. Второй проход обнаружил пять существенных пробелов:

| Замечание | Исправление плана |
| --- | --- |
| Custom-слайд не должен требовать уже опубликованного шаблона | Добавлены локальная композиция, экземпляры блоков и явное сохранение в библиотеку |
| HTML snapshot не восстанавливает структурированный editable PPTX сам по себе | Снимок объявляет автономные форматы; нужны подготовленные export-данные или закреплённые реализации |
| Структурированный PPTX может получить второй конкурирующий документ | E3 условно зависит от F3/export-представления; контент и порядок берутся из общей подготовки |
| PDF и полная упаковка ресурсов не являются техническими prerequisites сохранения документов | Экспортная и документная ветки разделены после общего runtime; F4 сериализует, G1 обеспечивает файловую надёжность |
| Ссылки набора ломаются при rename/delete, если адресовать их именем | Постоянные ID, область уникальности, duplicate с новым ID и явное missing-reference состояние |

Экспортный разбор сузил четыре непроверенных обещания: совпадение HTML относится к заявленному профилю и закреплённой среде; PDF требует явного print/screen, размера и фона; offline-переносимость относится к включённым ресурсам и разрешённым шрифтам; первый PPTX-spike ограничен тремя примерами, широкая матрица добавляется после предварительного выбора backend.

По документации Playwright `page.pdf()` использует print media, фон по умолчанию выключен, а приоритет CSS-размера страницы требует настройки. Поэтому совпадение с PNG входит в отдельную приёмку PDF. DOM to PPTX описывает поддерживаемое подмножество DOM/CSS; PptxGenJS предоставляет API текстовых объектов, фигур и изображений и требует собственного представления раскладки. Выбор между ними отложен до испытания, а не принят по списку функций.

Ни DOM-to-PPTX, ни PptxGenJS в этом ревью не устанавливались и не испытывались. PNG/PDF/PPTX-критерии новых этапов — план проверок, не результаты выполненного экспорта.
