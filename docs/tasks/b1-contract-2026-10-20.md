# B1 Контракт Project Deck Slide

Дата: 20 октября 2026 года. Область — описание контракта и перехода от 0.1, без реализации B2–B4 и без изменений потребителей. Статус: проект решений подготовлен для обсуждения. Публичная поддержка v1 ещё не реализована; версия npm-релиза не назначена.

## Результат

- [Контракт Project Deck Slide](../contracts/project-deck-slide-v1.md): область сущностей, ID/порядок/пути, два источника, размеры, пустые состояния, артефакты и минимальная проекция чтения.
- [Карта перехода 0.1 → v1](../migrations/project-contract-v1.md): поля, unversioned bridge, сохранение старых путей и callbacks, до/после, границы автоматизации и откат.

Предложены постоянные ID экземпляров внутри Deck, отдельные index/number и artifactNo для старых файлов; registered-конфигурация — единственный источник состава. Discovery — явный read-only режим. Stable layout используется новыми конфигами по умолчанию, legacy layout сохраняет цифровые пути через явную привязку. Абсолютный root сохраняет прежний смысл исходной базы артефактов.

Версия контракта HTML-адаптера отделена от будущей схемы сохраняемого документа. data остаётся непрозрачным для движка; библиотека шаблонов/блоков не требуется от HTML-проекта. callbacks, публичные методы и CLI остаются оболочками над будущей общей моделью; v1 не объявляется готовым после одного нового парсера.

## Ревью решений

Выполнено независимое read-only архитектурное ревью двух документов. Уточнены:

1. Грамматика и уникальность artifactPrefix, запрет prefix в stable layout.
2. Ограничение автоматического переноса буквенных no и случай case-only/дублирующихся ссылок.
3. Preflight имён отчётов и конфликтов с каталогами, включая изменение времени вызова reportName.
4. Версионированная проекция чтения и compatibility-представление: старое no не становится новым number.
5. Registered root до первого рендера: missing допустим, отсутствие источника discovery — отдельная ошибка.

Сравнены варианты глобальных ID, ID от позиции, старых flat-путей, скрытого merge и обязательного JSON-контракта. Причины выбора и издержки записаны в самом контракте. В migration-примере применяется явная таблица привязок; она не зависит от object identity или текущего индекса массива.

## Проверки

Проверены UTF-8 и локальные Markdown-ссылки всех 10 документов; повреждённых символов и отсутствующих целей нет. Четыре JS-блока прошли синтаксическую проверку и ограниченное выполнение как примеры: discovery-профиль, HTML registered-примера и старый/новый wrapper с одинаковым HTML. Привязка data.source сохраняется при копировании метаданных; ID и artifactNo в таблице явные. Это проверка примеров, а не реализация нормализатора.

Повторное независимое ревью подтвердило снятие пяти замечаний и обнаружило последнее противоречие: описание проекции чтения ошибочно распространяло авторский порядок/ID экземпляра на discovery. Оно исправлено явным различием двух режимов; index/number вычисляются по порядку каждого источника.

SHA-256 всех 7 runtime-файлов совпадает с registry-архивом 0.1.0 и исходной точкой A. `git diff --check` прошёл. Реализация, зависимости, CLI, workflows и fixtures в B1 не менялись; существующие незакоммиченные изменения этапа A сохранены. Runtime-тесты повторно не запускались, поскольку этот шаг меняет только документацию. Будущая матрица B2–B4 является спецификацией, а не выполненными тестами нового runtime.

При повторной сверке исходников исправлена неточность baseline и исторического ревью: renderQa уже ожидается через await и допускает Promise строки. reportName/issueCount остаются синхронными. Изменён только текст описания, не реализация.
